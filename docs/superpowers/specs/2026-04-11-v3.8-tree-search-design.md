# v3.8 — Hierarchical Proof Search with Microkernel GVR

## Overview

v3.8 replaces the whole-solution Generate→Verify→Revise loop with a **hierarchical proof search** that operates at the atom level. A complete solution is an initial "bridge" — a hypothesis about the path from premises to conclusion. Stepwise verification identifies which atoms hold (anchors) and which fail (gaps). The GVR loop then operates as a **microkernel** scoped to individual gaps, while an outer search layer manages the proof structure via PUCT-guided gap selection and Alien-Science-inspired technique exploration. Gaps that resist filling are recursively subdivided; proof paths that resist completion are abandoned and re-bridged.

## Motivation

The current architecture wastes compute. When a 10-step solution has one flawed step, the entire solution is regenerated — discarding 9 correct steps. Stepwise verification (v3.3's `verify_step_N()`) and atom annotations (v3.5) already identify *which* steps are correct, but the GVR loop cannot exploit this knowledge. v3.8 closes this gap.

**Inspirations:**
- **Aletheia** (arXiv:2602.10177): The GVR loop — generate, verify, revise. Becomes the microkernel.
- **Brenner et al.** (arXiv:2603.04735): Step-level decomposition with executable verification. Each node is an intermediate result paired with a Python verifier. Verification-driven pruning eliminated 80% of 600 explored nodes.
- **Alien Science** (arXiv:2603.01092): Idea decomposition into recombinable atoms scored by coherence × novelty. Guides exploration toward non-obvious bridging techniques when standard approaches fail.

None of these papers implement the combined architecture described here.

## Architecture

```
┌──────────────────────────────────────────────────────────────┐
│  Search Layer                                                 │
│  Manages proof graph. PUCT selects gaps. Triggers re-bridge.  │
│                                                               │
│  ┌──────────────────────────────────────────────────────────┐ │
│  │  Exploration Layer (per gap)                             │ │
│  │  Enumerates bridging techniques. Scores coherence ×      │ │
│  │  novelty. PUCT selects technique.                        │ │
│  │                                                          │ │
│  │  ┌────────────────────────────────────────────────────┐  │ │
│  │  │  GVR Microkernel                                   │  │ │
│  │  │  Generate atom replacement → Verify atom →         │  │ │
│  │  │  Revise atom. Scoped between anchored neighbors.   │  │ │
│  │  └────────────────────────────────────────────────────┘  │ │
│  └──────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

**Layer 1 — Search**: Owns the proof graph. Picks which gap to work on via PUCT. Detects when a proof path is dead and triggers re-bridging. Manages budget.

**Layer 2 — Exploration**: Per gap. Asks: "What techniques could bridge anchor A to anchor B?" Scores each by coherence (will it work?) and novelty (have we tried it?). PUCT selects which technique to attempt.

**Layer 3 — GVR Microkernel**: The existing `generate()`, `verify()`, `revise()` subagent calls, retargeted to operate on a single atom with its anchored neighbors as fixed context.

## Data Structures

### AtomNode (extends AtomAnnotation)

```python
@dataclass
class AtomNode:
    # From existing AtomAnnotation
    id: int
    deps: tuple[int, ...]
    oracle: OracleType
    content: str
    synthetic: bool = False

    # v3.8 additions
    status: Literal["pending", "anchored", "failed", "subdivided"] = "pending"
    level: int = 0                          # subdivision depth
    parent_id: int | None = None            # atom this was subdivided from
    child_ids: list[int] = field(default_factory=list)

    # PUCT state (for gaps)
    visit_count: int = 0
    total_value: float = 0.0                # sum of verification confidences
    techniques_tried: list[str] = field(default_factory=list)

    @property
    def q_value(self) -> float:
        return self.total_value / self.visit_count if self.visit_count else 0.0
```

### ProofGraph

```python
@dataclass
class ProofGraph:
    atoms: dict[int, AtomNode]              # id → node
    next_id: int                            # monotonic ID counter

    def gaps(self) -> list[AtomNode]:
        """Return all failed atoms, ordered by ID."""

    def anchors(self) -> list[AtomNode]:
        """Return all verified atoms."""

    def neighbors(self, atom_id: int) -> tuple[AtomNode | None, AtomNode | None]:
        """Return (left_anchor, right_anchor) flanking a gap."""

    def subdivide(self, atom_id: int, n_children: int) -> list[int]:
        """Replace atom with n_children sub-atoms. Returns new IDs.
        Parent becomes 'subdivided'. Children inherit deps."""

    def downstream(self, atom_id: int) -> list[int]:
        """Return atom IDs that transitively depend on this atom."""

    def is_complete(self) -> bool:
        """True when every atom is anchored (or subdivided with all children anchored)."""
```

### Inter-layer Messages

```python
@dataclass(frozen=True)
class MicrokernelTask:
    gap_id: int
    left_anchor: str                        # content of left neighbor
    right_anchor: str                       # content of right neighbor
    technique: str                          # bridging technique description
    problem_context: str                    # original problem statement
    max_revisions: int

@dataclass(frozen=True)
class MicrokernelResult:
    status: Literal["filled", "failed", "too_large"]
    replacement_content: str                # new atom content (if filled)
    confidence: float
    critique: str                           # verifier feedback (if failed)
    error_category: str                     # from classify_errors()
```

## Algorithm

```
solve(problem, config):
    bridge_attempts = 0
    failed_bridges = []
    best_solution = None
    best_confidence = 0.0

    while bridge_attempts < config.max_bridges and budget_remaining():

        # ── Phase 1: Bridge ──────────────────────────────────
        solution = generate_full_solution(problem, excluded=failed_bridges)
        graph = decompose_into_atoms(solution)

        # ── Phase 2: Stepwise Verification ────────────────────
        for atom in graph.atoms_in_order():
            result = verify_atom(atom, graph.neighbors(atom.id))
            atom.status = "anchored" if result.acceptable else "failed"

        if graph.is_complete():
            return solution  # solved on first bridge

        # ── Phase 3: Gap-Filling Search ───────────────────────
        while graph.gaps() and budget_remaining():
            gap = puct_select_gap(graph)

            if gap is None:
                break  # all gaps exhausted (visited ≥ technique_budget times) → re-bridge

            # Alien-explore: enumerate bridging techniques
            techniques = enumerate_techniques(
                left=graph.neighbors(gap.id)[0],
                right=graph.neighbors(gap.id)[1],
                tried=gap.techniques_tried,
            )
            technique = puct_select_technique(techniques, gap)

            # GVR microkernel
            result = gvr_microkernel(MicrokernelTask(
                gap_id=gap.id,
                left_anchor=graph.neighbors(gap.id)[0].content,
                right_anchor=graph.neighbors(gap.id)[1].content,
                technique=technique,
                problem_context=problem,
                max_revisions=config.revision_budget(gap),
            ))

            # Update graph
            if result.status == "filled":
                gap.content = result.replacement_content
                gap.status = "anchored"
                gap.visit_count += 1
                gap.total_value += result.confidence
                propagate_reverify(graph, gap.id)

            elif result.status == "too_large" and gap.level < config.max_depth:
                graph.subdivide(gap.id, n_children=2)
                # children enter the gap pool for next iteration

            else:  # failed
                gap.visit_count += 1
                gap.total_value += result.confidence
                gap.techniques_tried.append(technique)

            # Track best seen
            current = assemble_solution(graph)
            if current.confidence > best_confidence:
                best_solution, best_confidence = current, current.confidence

            if graph.is_complete():
                return assemble_solution(graph)

        # ── Phase 4: Re-bridge ────────────────────────────────
        failed_bridges.append(summarize_failed_path(graph))
        bridge_attempts += 1

    return best_solution  # UNSOLVED — return best seen
```

## PUCT Scoring

### Gap Selection

When multiple gaps exist, PUCT selects which to work on:

```
PUCT(gap) = Q(gap) + c_puct · P(gap) · √(N_total) / (1 + N(gap))
```

- **Q(gap)**: Mean verification confidence across all attempts on this gap. Higher Q = closer to solution.
- **P(gap)**: Prior probability. Default: `1/n_gaps`. Can be weighted by error category — `algebra` gaps get higher prior (mechanically fixable), `logic` gaps get lower (likely need different technique).
- **N(gap)**: Visit count for this gap.
- **N_total**: Sum of all gap visit counts.
- **c_puct**: Exploration constant (default 1.414).

### Technique Selection (within a gap)

```
PUCT(tech) = coherence(tech) + c_puct · novelty(tech) · √(N_gap) / (1 + N(tech))
```

- **coherence(tech)**: LLM-estimated probability that this technique connects the two anchors. Range [0, 1].
- **novelty(tech)**: Inverse of availability. Untried techniques get `novelty = 1.0`; previously failed techniques get `novelty = 0.1`.
- **N(tech)**: Times this technique has been attempted for this gap.
- **N_gap**: Total technique attempts for this gap.

## Alien Exploration

For each gap, the exploration layer asks:

> Given that step [LEFT_ANCHOR] is established and step [RIGHT_ANCHOR] must follow, list 3-5 distinct mathematical techniques or lemmas that could bridge this gap. For each, rate your confidence that it would work (0.0 to 1.0).

The response provides technique names and coherence scores. Techniques already in `gap.techniques_tried` are filtered out. The remaining candidates are scored by PUCT (coherence as Q, novelty as prior) and the top technique is selected.

**Cost**: ~1K tokens per enumeration call. Called at most once per gap per exploration round (cached until a technique succeeds or all enumerated techniques are exhausted, triggering re-enumeration).

**Bidirectional bridge hint**: The enumeration prompt can optionally include both a forward hint ("continuing from [LEFT_ANCHOR], what follows?") and a backward hint ("to reach [RIGHT_ANCHOR], what's needed?"). The LLM's technique proposals naturally bridge these two directions.

## Recursive Subdivision

When the GVR microkernel returns `too_large` (the gap between two anchors is too wide for a single-step bridge):

1. Ask the LLM: "What intermediate result would you expect between [LEFT] and [RIGHT]?"
2. Create a new intermediate atom at `level = parent.level + 1`
3. The parent atom gets `status = "subdivided"`, the two children enter the gap pool
4. Recursion depth bounded by `config.max_subdivision_depth` (default: 2)

**"Too large" trigger**: Two signals, either sufficient:
1. **Verifier-detected**: The critique indicates the gap requires multiple logical steps (phrases like "several steps omitted", "non-trivial intermediate result").
2. **Failure-count**: The microkernel fails `K` times on the same gap without subdivision (default K=3). This catches cases where the verifier doesn't explicitly flag complexity but the gap resists all techniques.

**`assemble_solution(graph)`**: Concatenate all anchored atom contents in dependency order (topological sort of the atom DAG). For subdivided atoms, recursively include their children's content. Returns a `Solution` with aggregate confidence = min(atom confidences).

## Re-bridging

When the gap-filling search exhausts its budget without completing the proof:

1. Summarize the failed path: which atoms anchored, which gaps resisted, which techniques failed
2. Add to `failed_bridges` list (analogous to existing `failed_approaches`)
3. Generate a completely new solution with `STRATEGY_RESET_ADDENDUM` injecting the failed bridge summary
4. Decompose and restart from Phase 2

Re-bridging is bounded by `config.max_bridges`. After the last bridge, return `Verdict.UNSOLVED` with the best solution assembled from the highest-confidence atoms across all bridges.

## Cost Model

**Current (flat GVR)**: Each iteration regenerates the full solution. For a 10-atom solution over 5 iterations: ~50 atom-equivalents of generation + 5 full verifications.

**v3.8 (tree search)**: Initial bridge (1 full generation + K atom verifications). Then ~2-3 gap-filling cycles per gap, each generating/verifying a single atom. For a 10-atom solution with 2 gaps, 3 techniques per gap: ~10 atom-generations + 10 + 6 atom-verifications = ~26 atom-equivalents.

**Net**: Comparable total tokens for easy problems (overhead of stepwise verification offsets savings). Significant savings for problems where most atoms are correct but 1-2 steps are wrong — the common case for near-correct solutions.

## Open Questions

1. **Atom granularity**: The current Generator produces ~5-15 atoms per solution. Should v3.8 prompt for a specific atom count, or accept whatever the Generator produces?

2. **Stepwise verification cost**: Verifying K atoms individually costs K API calls. Should atoms be batched into a single verification call with structured output?

3. **Subdivision trigger**: GVR failure count threshold (e.g., 3 failures → auto-subdivide) vs. verifier-detected complexity?

4. **Variant-B interaction**: Apply variant-B diversity at the bridge level (different models for different bridges), the technique level (different models for different gap-filling approaches), or both?

5. **Skill parity**: The skill orchestrator cannot use `ThreadPoolExecutor`. Atom-level parallelism in the library (verify all atoms concurrently) has no skill equivalent. Accept this asymmetry, or design the skill to be sequential-only?
