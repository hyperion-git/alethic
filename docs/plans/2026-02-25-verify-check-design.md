# Verify & Check Commands — Design Document

**Date:** 2026-02-25
**Status:** Proposed
**Scope:** Python library + Claude Code skills + CLI

## Problem

Alethic currently only produces and verifies solutions as part of the
Generate-Verify-Revise loop. There is no way to independently assess an
existing solution or derivation — whether produced by Alethic, written by
hand, or generated by another tool.

Two distinct use cases exist:

**Use case 1 — Verify.** "I have a problem and a proposed solution. Is the
solution correct?" Requires both a problem statement and a solution. Evaluates
correctness, completeness, and relevance to the stated problem.

**Use case 2 — Check.** "I have a derivation. Is the reasoning internally
valid?" Requires only the solution/derivation text. Evaluates logical validity,
algebraic correctness, dimensional consistency, and absence of unjustified
claims or circular reasoning. Does not evaluate whether the work answers any
particular question.

Both use cases benefit from multi-verifier consensus — running K independent
verifiers and synthesizing their assessments — to achieve higher confidence
than a single verification pass.

## Conceptual Model

| | `verify` | `check` |
|---|---|---|
| **Input** | Problem + solution | Solution only |
| **Question** | "Does this correctly solve the stated problem?" | "Is this reasoning internally valid?" |
| **Focus** | Correctness, completeness, relevance | Logic, algebra, dimensions, no leaps, no circularity |
| **Domain** | Auto-detected, `--domain` override | Auto-detected, `--domain` override |
| **Output** | Synthesized ConsensusResult | Synthesized ConsensusResult |
| **Mutates input?** | No — read-only assessment | No — read-only assessment |

Shared pipeline:

```
Input → Domain Detection → K Parallel Verifiers → Mechanical Aggregation → LLM Critique Cleanup → Synthesized Report
```

The only difference between verify and check is the prompt templates and
evaluation criteria. The orchestrator, synthesis pipeline, tool sandbox, and
output format are identical.

## Domain Auto-Detection

A static classification dictionary (`domain-keywords.json`) maps ~500 terms
per domain across three weighted tiers:

| Tier | Weight | Size per domain | Examples (physics) | Examples (math) |
|------|--------|-----------------|--------------------|-----------------|
| strong | 3 | ~50 | Hamiltonian, Lagrangian, Schrodinger, wavefunction | theorem, proof, lemma, conjecture, iff |
| moderate | 2 | ~150 | energy, momentum, potential, force | polynomial, convergence, topology, manifold |
| weak | 1 | ~300 | conservation, symmetry, spectrum | function, set, map, ring |

Detection algorithm: scan solution text for dictionary terms, sum weighted
scores per domain, highest score wins. Ties default to math. Ambiguous results
noted in output with suggestion to use `--domain` override.

The dictionary lives in `skills/alethic-common/references/domain-keywords.json`
(skills) and `src/alethic/data/domain-keywords.json` (Python library, shipped
via `importlib.resources`). One source of truth, generated by LLM and
human-curated before commit.

## Python Library Architecture

### New Modules

```
src/alethic/
  verifier_agent.py    # VerifierAgent (verify mode) and CheckerAgent (check mode)
  synthesizer.py       # synthesize() subagent + mechanical aggregation
  domain.py            # detect_domain() using domain-keywords.json
  data/
    domain-keywords.json
```

### New Classes

```python
@dataclass(frozen=True)
class VerifierConfig:
    model: str = "claude-sonnet-4-6"
    num_verifiers: int = 3                    # K
    tool_guidance: frozenset = frozenset({"sympy", "numpy", "scipy", "matplotlib"})
    domain: str | None = None                 # None = auto-detect
    thinking: bool = False
    thinking_budget: int = 15_000
    max_tokens: int = 16_384

    PRESETS = {
        "quick":    {"num_verifiers": 2, "thinking": False, "max_tokens": 16_384},
        "default":  {"num_verifiers": 3, "thinking": False, "max_tokens": 16_384},
        "thorough": {"num_verifiers": 5, "thinking": True,  "thinking_budget": 15_000, "max_tokens": 32_768},
        "extreme":  {"num_verifiers": 7, "thinking": True,  "thinking_budget": 40_000, "max_tokens": 65_536},
    }

    @classmethod
    def from_preset(cls, name: str, **overrides) -> "VerifierConfig": ...


class VerifierAgent:
    """Runs K independent verifications and synthesizes."""

    def __init__(self, config: VerifierConfig): ...

    def verify(self, problem: str, solution: str) -> ConsensusResult:
        """Problem + solution -> consensus verification."""

    def check(self, solution: str) -> ConsensusResult:
        """Solution only -> internal consistency audit."""


class CheckerAgent(VerifierAgent):
    """Thin subclass — injects check-specific prompts."""


@dataclass
class ConsensusResult:
    verdict: Verdict                               # majority vote (deterministic)
    confidence: float                              # mean of K (deterministic)
    confidence_range: tuple[float, float]           # (min, max) across K
    critique: str                                  # LLM-cleaned unified critique
    issues: list[ConsensusIssue]                   # union with vote counts
    individual_results: list[VerificationResult]   # raw K results
    domain_detected: str                           # "math" or "physics"
    num_verifiers: int                             # K used
    elapsed_seconds: float

    @property
    def consensus_ratio(self) -> str:
        """e.g. '3/3' or '2/3'."""


@dataclass
class ConsensusIssue:
    text: str
    severity: IssueSeverity
    flagged_by: int                                # how many of K flagged this
```

### Parallel Execution

K verifiers run in parallel via `ThreadPoolExecutor`, reusing the same pattern
as best-of-N generation in `MathAgent.solve()`. Each verifier call is an
independent `verify()` invocation from `subagents.py` with fresh context
(decoupled — no access to other verifiers' outputs).

### Synthesis Pipeline

1. **Mechanical aggregation** (deterministic, no LLM call):
   - Verdict: majority vote. No majority → most severe verdict (conservative).
   - Confidence: arithmetic mean of K values.
   - Issues: union, deduplicated by text similarity, each tagged with `flagged_by` count.

2. **LLM critique cleanup** (one cheap API call):
   - Reads all K raw critiques + mechanical aggregation.
   - Produces one coherent unified critique.
   - Does NOT override verdict or confidence — those are final from step 1.

## CLI Interface

New subcommands alongside `solve` and `derive`:

```
alethic verify <solution_file> --problem <text_or_file> [options]
alethic verify <session_dir> [options]
alethic check <solution_file> [options]
alethic check <session_dir> [options]
```

### Shared Flags

```
--preset {quick,default,thorough,extreme}   # controls K
--verifiers/-K <int>                        # override K directly
--domain {math,physics}                     # override auto-detect
--tools {sympy,numpy,scipy,matplotlib,none} # default: all four
--model/-m <model_id>                       # Claude model
--json                                      # structured JSON output
--quiet/-q                                  # suppress progress
```

### verify-Specific Flags

```
--problem/-p <text>          # inline problem statement
--problem-file/-P <file>     # read problem from file
```

### Input Resolution

1. If argument is a directory containing `session.json` → session mode
   (auto-extract problem + solution from existing alethic session).
2. If argument is a file → solution file mode.
3. For `verify`: problem required (from `--problem`, `--problem-file`, or session).
4. For `check`: no problem needed (ignored if session provides one).

### Default Tools

| Command | Default `--tools` |
|---|---|
| `verify` / `check` | `sympy,numpy,scipy,matplotlib` |
| `solve` / `derive` | `sympy,numpy` (unchanged) |

Follows the existing pattern — thin SKILL.md configurators loading a shared
orchestrator:

```
skills/
  alethic-common/
    orchestrator.md              # existing GVR loop (unchanged)
    verify-orchestrator.md       # NEW: shared verify/check loop
    references/
      domain-keywords.json       # NEW: classification dictionary
      synthesizer.md             # NEW: critique cleanup prompt
  alethic-verify/
    SKILL.md                     # thin configurator
    references/
      verifier.md                # verify-specific prompt (problem + solution)
      tools/
        sympy-verifier.md
        numpy-verifier.md
        scipy-verifier.md        # NEW
        matplotlib-verifier.md   # NEW
  alethic-check/
    SKILL.md                     # thin configurator
    references/
      checker.md                 # check-specific prompt (internal consistency)
      tools/
        sympy-verifier.md
        numpy-verifier.md
        scipy-verifier.md        # NEW
        matplotlib-verifier.md   # NEW
```

### verify-orchestrator.md

The shared loop, parameterized by the thin configurators:

```
Step 0: Parse input (session dir or file), auto-detect domain
Step 1: Launch K verifier sub-agents in parallel (Task tool)
        - Each gets fresh context (decoupled)
        - Each writes to worklog/verifier_{k}.md
Step 2: Mechanical aggregation
        - Majority-vote verdict
        - Mean confidence
        - Union issues with vote counts
Step 3: Synthesizer sub-agent (Task tool)
        - Reads all K reports + mechanical aggregation
        - Produces coherent unified critique
        - Does NOT override verdict/confidence
Step 4: Assemble final report, write output.md
```

### Placeholders Set by Thin Configurators

- `{mode}`: "verify" or "check"
- `{domain}`: auto-detected or overridden
- `{prompt_template}`: path to verifier.md or checker.md
- `{requires_problem}`: true/false
- `{default_tools}`: "sympy,numpy,scipy,matplotlib"
- `{num_verifiers_preset_table}`: the K preset mapping

### Session Directory Layout

```
.alethic/
  {slug}-verify-{YYYYMMDD}-{hex}/     # or {slug}-check-...
    session.json          # mode: "verify"|"check", consensus metadata
    problem.md            # verify only
    input.md              # the solution being assessed
    output.md             # synthesized report
    worklog/
      events.jsonl        # one JSON line per Task call
      verifier_1.md       # raw report from verifier 1
      verifier_2.md       # raw report from verifier 2
      verifier_3.md       # raw report from verifier 3
      aggregation.json    # mechanical aggregation (auditable)
      synthesis.md        # LLM-cleaned critique
```

No `iter{N}/` subdirectories (no iterative loop), no revision files. Flat
worklog with K verifier outputs.

## Prompt Design

### Verify Prompts (problem + solution)

Close to existing verifier prompts but standalone — no coupling to a GVR loop.

**System prompt** (sketch):
```
You are a rigorous mathematical/physical reviewer. You receive a problem
statement and a proposed solution. Your task is to determine whether the
solution correctly and completely solves the stated problem.

You have NO access to the author's reasoning process — only the final
solution text. You must independently verify every claim.

[tool guidance injected here based on --tools]
```

**Evaluation criteria** (structured output — same fields as existing
`VerificationResult`): VERDICT, CONFIDENCE, CRITIQUE, ISSUES,
SECTION_CONFIDENCES, REASON (false-premise detection).

Main change from existing verifier prompts: removal of any references to
"previous iterations" or "revision history" since verify is one-shot.

### Check Prompts (solution only, internal consistency)

Genuinely new — no existing prompt to adapt from.

**System prompt** (sketch):
```
You are a rigorous proof auditor. You receive a mathematical derivation or
physical argument WITHOUT the original problem statement. You evaluate ONLY:

1. Logical validity — does each step follow from the previous?
2. Algebraic correctness — are manipulations error-free?
3. Dimensional consistency — do units track correctly? (physics)
4. No unjustified claims — is every assertion proven or stated as assumption?
5. No circular reasoning — does the argument avoid assuming its conclusion?
6. Boundary/limiting cases — are edge cases consistent with the general result?

[tool guidance injected here]
```

**Verdict semantics shift for check:**

| Verdict | Verify meaning | Check meaning |
|---|---|---|
| CORRECT | Solves the stated problem | Internally valid reasoning |
| MINOR_ISSUES | Correct but with gaps | Valid but with minor sloppiness |
| MAJOR_FLAW | Incorrect answer | Contains logical/algebraic errors |
| UNSOLVED | Problem premise is false | Reasoning is incoherent/circular |

### Synthesizer Prompt

Shared by both verify and check. Lightweight — prose cleanup only.

```
You are a technical editor. You receive K independent verification reports
and a mechanical aggregation (verdict, confidence, issues with vote counts).

Produce ONE coherent, well-written critique that represents the consensus view.
You MUST NOT change the verdict or confidence — those are determined
mechanically and are final. You synthesize only the critique text.

Rules:
- Weight issues by how many reviewers flagged them
- Resolve contradictions explicitly
- Eliminate redundancy across reports
- Maintain severity classifications from the aggregation
- Be concise — this is a report, not an essay
```

### Domain-Specific Variations

Physics verify/check adds: dimensional analysis emphasis, limiting-case checks,
physical intuition assessment. Math verify/check adds: proof structure emphasis,
logical completeness, counterexample consideration. These live in the respective
`references/` directories, loaded by the orchestrator based on detected domain.

## Edge Cases

| Situation | Behavior |
|---|---|
| `verify` without problem (no session, no `--problem`) | Error: "verify requires a problem statement." |
| `check` given a problem (from session) | Silently ignore — checker prompts don't use it |
| Empty solution file | Error: "Solution file is empty." |
| All K verifiers disagree (no majority) | Verdict = most severe (conservative). Flag: "No consensus." |
| Domain auto-detection tie | Default to math. Note in output. |
| Very long solution (exceeds context) | Truncation warning + suggest splitting. |
| `--tools none` | All K verifiers run pure reasoning. |

## Scope Exclusions (YAGNI)

- No verify-then-revise loop (use solve/derive for that)
- No interactive mode
- No formal proof checker integration (Lean, Coq)
- No diffing between successive verify runs
- No webhook/CI integration
- No changes to solve/derive default tools (remain sympy,numpy)
