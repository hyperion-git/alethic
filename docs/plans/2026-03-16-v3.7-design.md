## 1. Conceptual Framework

### 1.1 The Routing Problem

Between v3.2 and v3.6, Alethic accumulated ~10 routing functions in `agent.py` that all
answer the same question: *given the current solve state, how should the next iteration
allocate compute?* These functions grew organically as features were added:

| Function | Lines | Added in | Decision |
|----------|-------|----------|----------|
| `rank_candidates()` | 75–87 | v3.4 | Candidate selection (DEAD CODE) |
| `_build_atom_focus_directive()` | 116–170 | v3.6 | Verifier attention routing |
| `_build_verifier_extra_system()` | 376–387 | v3.6 | Verifier system prompt assembly |
| `_check_stall()` | 389–410 | v3.2 | Stall detection → reset trigger |
| `_compute_dynamic_n()` | 411–433 | v3.4 | N escalation by difficulty |
| `_compute_adaptive_revisions()` | 435–446 | v3.4 | Revision budget by error type |
| `_build_reset_context()` | 448–473 | v3.2 | Strategy reset prompt |
| `_build_atom_context()` | 475–533 | v3.5 | Atom stability advisory for reviser |
| `classify_errors_routed()` | error_taxonomy.py:154–163 | v3.4 | Error → oracle type (DEAD CODE) |

Additionally, the main loop at lines 978–1200 contains inline routing: EvidenceState
construction (1132–1137), breaker dispatch (1156), and acceptance gating.

The problem is not that these functions are wrong — they're well-tested and correct. The
problem is that their interactions are implicit. `_compute_dynamic_n()` and
`_check_stall()` both read confidence history but don't coordinate. The stall reset
injects `reset_n_boost` into N *additively* on top of dynamic N, but that interaction is
expressed as an `if is_reset` branch in the main loop, not as a composable decision.

### 1.2 The v3.7 Consolidation

`OracleRouter` is a pure-function routing layer: it reads `RunState` + `EvidenceState`,
produces a `RoutingDecision` dataclass, and never mutates state. The agent.py main loop
becomes a consumer of routing decisions rather than a producer of them.

This is a **strangler fig refactor**: the router wraps existing decisions without changing
behavior. All routing functions move to `oracle_router.py`; agent.py's main loop
simplifies to `decision = self.router.route(state, evidence)` followed by action
dispatch. Tests for the individual functions remain valid — they just import from
`oracle_router` instead of `agent`.

The refactor creates the extension point that v3.8 needs: tree search replaces the
router's `rank_candidates()` method with PUCT scoring, and adds a `SearchPath` interface
that the router evaluates. No changes to agent.py's action dispatch.

### 1.3 The Symmetric Gate

The v3.8 decision is: **Option E** (atom-guided verification as primary strategy) or
**Option F** (PUCT tree search over atom graph). Currently we can measure atom
annotation rates (Option E data) but have no PUCT baseline (Option F data). This
creates an asymmetric gate — we'd compare measured atoms against unmeasured PUCT,
biasing toward whichever we measured.

v3.7 fixes this by measuring both on the same expanded benchmark:
- **Atom metrics**: annotation rate, directive coverage, per-problem atom counts
- **PUCT metrics**: UCB1 ranking divergence from confidence ranking

Both measured on the same 20-problem suite (10 math + 10 physics) → symmetric decision
input for v3.8.

## 2. OracleRouter Module

### 2.1 RoutingDecision Dataclass

```python
@dataclass(frozen=True)
class RoutingDecision:
    # Generation
    n_candidates: int               # candidates to generate this iteration
    is_reset: bool                  # stall reset triggered?
    reset_context: str | None       # generator prompt injection for reset

    # Verification
    verifier_extra_system: str | None  # extra system prompt (atom focus + adversarial)
    next_oracle: OracleType            # preferred oracle layer for this iteration
    force_adversarial: bool            # force adversarial self-correction?

    # Revision
    max_revisions: int              # revision budget for this iteration
    atom_context: str | None        # atom stability advisory for reviser
    error_category: str             # classified error from prior critique
    critique_addendum: str          # error-taxonomy-driven revision strategy
```

All fields are set once per iteration. The agent reads them; the router produces them.

### 2.2 OracleRouter Class

```python
class OracleRouter:
    """Pure-function routing layer for the GVR loop.

    Reads RunState + EvidenceState, produces RoutingDecision.
    Never mutates state — that remains the agent's responsibility.
    """

    def __init__(self, config: AgentConfig, domain: str):
        self._config = config
        self._domain = domain  # "math" or "physics"

    def route(
        self,
        state: RunState,
        evidence: EvidenceState,
    ) -> RoutingDecision:
        """Produce all routing decisions for the next iteration."""

        is_reset = self._check_stall(state)
        error_category, next_oracle, force_adversarial = self._classify_and_route(
            evidence.error_category
        )

        return RoutingDecision(
            n_candidates=self._compute_n(evidence, is_reset),
            is_reset=is_reset,
            reset_context=self._build_reset_context(state) if is_reset else None,
            verifier_extra_system=self._build_verifier_extra_system(state),
            next_oracle=next_oracle,
            force_adversarial=force_adversarial,
            max_revisions=self._compute_revisions(evidence),
            atom_context=self._build_atom_context(state),
            error_category=error_category,
            critique_addendum=get_revision_addendum(error_category),
        )

    def rank_candidates(
        self,
        verifications: list[VerificationResult],
    ) -> int:
        """Select best candidate index. Max-confidence in v3.7; PUCT in v3.8."""
        return max(
            range(len(verifications)),
            key=lambda i: verifications[i].confidence,
        )
```

### 2.4 Stall State Ownership

`_check_stall()` currently reads AND mutates `RunState` (increments
`iterations_since_meaningful_improvement`, enforces cooldown via
`last_reset_iteration`, caps `total_resets`). After extraction:

- **Router reads**: `state.confidence_history`, `state.stall_count`,
  `state.last_reset_iteration`, `state.consecutive_major_flaws`
- **Router returns**: `is_reset: bool` (the decision)
- **Agent mutates**: after consuming `is_reset`, the agent updates RunState counters

This preserves the principle that the router is a pure function. The agent is the
state machine; the router is the policy.

### 2.5 Dead Code Activation

**`classify_errors_routed()`** (error_taxonomy.py:154–163): Currently returns
`(category, OracleType, force_adversarial)` but is never called. The routing table
`_ORACLE_ROUTING` maps each error category to its preferred oracle layer. v3.7
activates this by having `OracleRouter._classify_and_route()` call
`classify_errors_routed()` and thread `next_oracle` + `force_adversarial` into
`RoutingDecision`.

**`rank_candidates()`** (agent.py:75–87): Currently a module-level function that is
defined, exported in `__init__.py`, tested in `test_rank_candidates.py`, but never
called. The real selection is an inline `list.sort(key=lambda x: x[1].confidence,
reverse=True)` at agent.py:708. v3.7 wires this by having `_verify_candidates()` call
`self.router.rank_candidates(verifications)` instead of the inline sort. The public
module-level `rank_candidates()` becomes a thin wrapper that delegates to a default
`OracleRouter` instance for backward API compatibility.

### 2.7 PhysicsAgent Impact

`PhysicsAgent` currently overrides `_adversarial_addendum()` and
`_reset_addendum()` to return physics-specific prompt strings. These are consumed by
`_build_verifier_extra_system()` and `_build_reset_context()` respectively.

After extraction, the router needs the domain-specific strings. Two options:

**Option A**: Router takes `adversarial_addendum_fn` and `reset_addendum_fn` callables
in its constructor. Agent passes `self._adversarial_addendum` and
`self._reset_addendum` at init time.

**Option B**: Router takes the addendum strings directly as constructor args. Agent
constructs them once and passes them in.

**Decision: Option A** — callables preserve the existing override pattern and allow
PhysicsAgent to simply construct a router with different functions. No change to
PhysicsAgent's override mechanism.

```python
# In MathAgent.__init__():
self.router = OracleRouter(
    config=self.config,
    domain=self._domain(),
    adversarial_addendum_fn=self._adversarial_addendum,
    reset_addendum_fn=self._reset_addendum,
)
```

### 2.8 Testing Strategy

Existing tests for individual routing functions (`test_stall_detection.py`,
`test_dynamic_n.py`, `test_rank_candidates.py`, etc.) are updated to import from
`oracle_router` instead of `agent`. A new integration test suite validates the
composed `route()` method:

- `test_route_first_iteration()` — no stall, no adaptive compute, baseline decisions
- `test_route_stall_triggers_reset()` — stall detected → `is_reset=True`, N boosted
- `test_route_hard_problem_escalates_n()` — low confidence + logic error → max N
- `test_route_algebra_error_reduces_revisions()` — algebra + high confidence → 1 revision
- `test_route_dead_code_now_active()` — `next_oracle` reflects `_ORACLE_ROUTING` table
- `test_route_pure_function()` — calling `route()` twice with same input → same output

### 4.1 Metrics

| Metric | Definition | Signal |
|--------|-----------|--------|
| `annotation_rate` | Fraction of iterations where `parse_atoms()` returned ≥1 non-synthetic atom | Option E activation frequency |

- `mean_directive_coverage` across all problems

## 5. PUCT Scoring Experiment

### 5.1 The Flat-Pool PUCT Approximation

Without tree search, PUCT scoring is evaluated post-hoc on the flat candidate pool
accumulated across iterations. The key question: **does PUCT reorder candidates
differently than pure confidence ranking?**

In a tree, PUCT balances exploitation (high-confidence nodes) against exploration
(under-visited branches). In the flat pool, we approximate "branches" as **approach
types** — classified by the error category of the first failing verification, or by
atom structure hash for passing solutions.

### 5.2 Approach Classification

Each candidate is tagged with an approach type:

```python
def classify_approach(solution: str, verification: VerificationResult) -> str:
    """Classify a candidate's approach for PUCT visit tracking."""
    if verification.is_acceptable(threshold=0.0):
        # Passing: hash the atom structure (atom IDs + deps)
        atoms = parse_atoms(solution)
        return "pass:" + _atom_structure_hash(atoms)
    else:
        # Failing: use error category
        return "fail:" + classify_errors(verification.critique)
```

This creates a vocabulary of approach types: `"pass:a3f2b1"`, `"fail:algebra"`,
`"fail:logic"`, etc. Repeated approaches share a type; novel approaches get unique
types.

### 5.3 UCB1 Score Computation

```python
import math

def ucb1_score(
    confidence: float,
    visit_count: int,
    total_visits: int,
    exploration_weight: float = 1.41,  # sqrt(2)
) -> float:
    """UCB1 score for a candidate's approach type."""
    if visit_count == 0:
        return float('inf')  # unvisited approach → explore
    exploitation = confidence
    exploration = exploration_weight * math.sqrt(
        math.log(total_visits) / visit_count
    )
    return exploitation + exploration
```

For each candidate in each iteration:
1. Look up its approach type's visit count (how many prior candidates shared this type)
2. Compute UCB1 score
3. Compare UCB1 ranking to confidence ranking

### 5.4 Comparison Column

`run_benchmark()` output gains a per-problem `puct_divergence` field:

```json
{
  "id": "sqrt2-irrational",
  "puct_divergence": {
    "reordered_iterations": 2,
    "total_iterations": 5,
    "divergence_rate": 0.40,
    "best_by_confidence": "candidate_0",
    "best_by_puct": "candidate_1",
    "puct_would_have_won": true
  }
}
```

`divergence_rate` = fraction of iterations where PUCT and confidence disagree on the
best candidate. If this is consistently >0.2 across the benchmark, PUCT has signal and
v3.8 tree search is justified. If <0.1, confidence ranking is sufficient.

### 5.5 Implementation Scope

~30 lines in a new function `compute_puct_comparison()` in `eval/harness.py`. Called
after each problem completes, consuming the `AgentResult.events` log to reconstruct
per-iteration candidate lists. No changes to the agent itself — purely post-hoc
analysis.

## 6. v3.8 Tree Design Sketch

This section is **documentation only** — no code ships in v3.7. It shows how v3.8
tree search would compose with the OracleRouter, establishing that the router's
interface is sufficient.

### 6.1 TreeNode Structure

```python
@dataclass
class TreeNode:
    """A node in the search tree. Each node represents a solution state."""
    solution: str                          # solution text at this node
    verification: VerificationResult | None  # None for unexpanded nodes
    parent: TreeNode | None
    children: list[TreeNode]
    visit_count: int = 0
    total_value: float = 0.0               # sum of confidence from all visits
    approach_type: str = ""                 # from classify_approach()

    @property
    def mean_value(self) -> float:
        return self.total_value / self.visit_count if self.visit_count else 0.0
```

### 6.2 SearchPath Interface

```python
@dataclass(frozen=True)
class SearchPath:
    """A path through the search tree from root to a leaf."""
    nodes: tuple[TreeNode, ...]
    depth: int
    cumulative_confidence: float

    def leaf(self) -> TreeNode:
        return self.nodes[-1]
```

### 6.3 OracleRouter as Tree-Node Evaluator

The router's `route()` method works at both levels:

- **Flat mode (v3.7)**: `route(state, evidence)` → single `RoutingDecision` for the
  next iteration. This is what ships.
- **Tree mode (v3.8)**: `route(state, evidence, search_path)` → `RoutingDecision`
  informed by the path context. The `search_path` parameter provides:
  - Depth → influences `n_candidates` (fewer candidates deeper in the tree)
  - Ancestor verdicts → influences `next_oracle` (if parent had a FIXABLE verdict,
    try L2 consistency check before full L3)
  - Visit counts → influences `rank_candidates()` via PUCT scoring

The v3.7 `route()` signature does not include `search_path` — it is added in v3.8 as
an optional parameter with default `None`.

### 6.4 rank_candidates → PUCT Scoring

v3.7 `rank_candidates()` returns `max(confidence)`. v3.8 replaces this with:

```python
def rank_candidates(
    self,
    verifications: list[VerificationResult],
    visit_counts: list[int] | None = None,
    parent_visits: int = 1,
) -> int:
    if visit_counts is None:
        # Flat mode: max confidence (v3.7 behavior)
        return max(range(len(verifications)), key=lambda i: verifications[i].confidence)
    # Tree mode: PUCT scoring
    scores = [
        ucb1_score(v.confidence, vc, parent_visits)
        for v, vc in zip(verifications, visit_counts)
    ]
    return max(range(len(scores)), key=lambda i: scores[i])
```

The v3.7 experiment (Section 5) measures divergence using this exact scoring function,
so the v3.8 implementation is a direct promotion of the experiment code.

## 9. Gate Criteria for v3.8

v3.7 benchmark results must show three things:

### 9.1 Atom Metrics (Option E data)

| Metric | Threshold | Signal |
|--------|-----------|--------|
| `mean_annotation_rate` | ≥ 0.50 | Generator produces atoms often enough to be useful |
| `mean_directive_coverage` | ≥ 0.30 | Directives actually engage (not all-monolithic) |
| `median_atom_count` | ≥ 3 | Atoms are granular (not trivially K=1 with one real atom) |

If annotation rate < 0.30: atom-guided verification is inert for most problems.
Strengthen generator prompt further or reconsider atom format before v3.8.

### 9.2 PUCT Metrics (Option F data)

| Metric | Threshold | Signal |
|--------|-----------|--------|
| `mean_divergence_rate` | ≥ 0.20 | PUCT reorders candidates meaningfully |
| `puct_would_have_won` count | ≥ 3/20 problems | PUCT selection would have solved problems that confidence ranking missed |

If divergence rate < 0.10: confidence ranking is sufficient, tree search adds complexity
without benefit. Defer v3.8 tree search.

### 9.3 Combined Decision Rule

```
gate(atom_data, puct_data):
    atom_improvement = delta_solve_rate_with_atoms / baseline_solve_rate
    puct_signal = puct_would_have_won_count / total_problems

    if atom_improvement >= 0.10:
        return "Option E: atom-guided verification as primary strategy"
    elif puct_signal >= 0.15:
        return "Option F: PUCT tree search over atom graph"
    else:
        return "Neither: ship v3.7 as v4.0 baseline, revisit architecture"
```

Both measured on the same 20-problem suite → symmetric decision input.

| Step | Estimated scope |
|------|----------------|
| rank_candidates wiring | ~20 lines changed |
| OracleRouter extraction | ~400 lines moved, ~50 new (RoutingDecision, route()), ~100 test updates |
| Physics benchmark | ~150 lines JSON + ~30 lines test |
| Atom measurement | ~50 lines in harness + ~30 lines test |
| PUCT experiment | ~30 lines in harness + ~20 lines test |
| Doc updates | CLAUDE.md module map, this design doc finalized |

### 11.2 Runtime Cost

OracleRouter extraction is a zero-cost refactor — same functions, same calls, different
file. No new API calls. Benchmark runs are developer-time costs only (estimated ~$15–25
per 20-problem default-preset run on Opus 4.6).

### 11.3 Risk Assessment

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| Benchmark scope creep (>2 days) | MEDIUM | Strict timebox; ship 8 problems if needed |
| OracleRouter extraction introduces regression | LOW | All routing functions have existing tests; move-only refactor |
| PUCT experiment shows no signal | MEDIUM | This is data collection, not commitment; null result is informative |
| Atom annotation rate too low for measurement | MEDIUM | v3.6 prompt strengthening targeted ~65%; measure to confirm |
