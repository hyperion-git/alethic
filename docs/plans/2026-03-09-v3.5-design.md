**Date:** 2026-03-09
**Milestone:** v3.5 — Idea Atoms + Adversarial Breaker (Phase 1 of Unified Framework)
**Features:** Atom Annotation Format, Adversarial Breaker, Atom-Aware Stall Recovery
**Research basis:** "Alien Science" (arXiv:2603.01092) — idea decomposition + RRF sampling
**Architecture synthesis:** 10 parallel investigation agents + 9 review agents (4 Section 1, 5 Sections 2-3)
**Rollout tier:** v3.5 (Phase 1) → v3.6 (Phase 2: atom-guided verification + web search) → v4.0 (gated on benchmark: tree search or full atom graph)

## 1. Conceptual Framework

### 1.1 The Unifying Principle: Idea Atoms as Metadata Overlay

The "Alien Science" paper (arXiv:2603.01092) introduces *idea atoms* — granular
conceptual units decomposed from problems/solutions, scored on coherence and cognitive
availability, sampled via Reciprocal Rank Fusion (RRF). Alethic v3.5 adapts this
framework as a **metadata overlay** on existing infrastructure rather than a
replacement.

Solutions remain monolithic text. The generator embeds lightweight atom annotations
inline — boundaries, dependency declarations, oracle-level obligations, and
`verify_atom_N()` functions — extending the existing `verify_step_N()` /
`ALETHIC_L{N}_CHECK:` sentinel pattern shipped in v3.4.

This enables three capabilities from a single primitive:
- **Adversarial breaking**: decompose solution into atoms, target weakest atoms
- **Stall recovery**: identify stable vs. oscillating atoms, preserve partial progress
- **Tree search preparation (v4.0)**: atoms become natural branching points with
  dependency-derived independence structure

The key insight is **primal-dual duality**: generation (constructive), verification
(evaluative), and breaking (adversarial constructive) all operate on the same atom
vocabulary — the generator creates atoms, the verifier scores them, the breaker tries
to kill them.

### 1.2 Design Principles

1. **Metadata overlay, not replacement**: Atoms annotate existing structure.
   Unparseable annotations degrade gracefully to plain text.
2. **No new API calls for classification**: Atom stability classification uses content
   hashing — zero compute overhead. Only the breaker adds API calls (Sonnet, 1-3 per
   session).
3. **Backward compatible**: Solutions without atom annotations trigger monolithic
   fallback — identical behavior to v3.4.
4. **Incremental rollout**: Each section is independently shippable. Section 1 is
   prerequisite for Section 3; Section 2 works standalone.

## 2. Section 1: Atom Annotation Format

### 2.1 Format Specification

```
K_ATOMS=5

ATOM[1] deps=[] oracle=L0
  We begin by establishing the coordinate system...
  ```python
  def verify_atom_1():
      ...
      print("ALETHIC_L0_CHECK: DIMENSIONS OK")
  ```

ATOM[2] deps=[1] oracle=L2
  Applying the Fourier transform to both sides...
  ```python
  def verify_atom_2():
      ...
      print("ALETHIC_L2_CHECK: CONSISTENCY OK (3.14159==3.14159)")
  ```

ATOM[3] deps=[1,2] oracle=L3
  The boundary conditions require that...
  (No programmatic check — requires LLM verification)
```

**Grammar rules:**
- IDs are **fixed integers** (1 through K), not descriptive names — ensures
  cross-iteration stability for stall recovery
- Generator declares `K_ATOMS=N` at the start of the solution
- `deps` is a list of atom integers this atom logically depends on
- `oracle` is the minimum verification ladder level needed (L0-L4)
- Atoms with `oracle=L0/L1/L2` MUST include a `verify_atom_N()` function
- Atoms with `oracle=L3/L4` have no programmatic check — verified by LLM or consensus
- If the generator omits annotations entirely, the solution is treated as a single
  implicit atom (backward compatible)

### 2.2 Data Model

```python
@dataclass(frozen=True)
class AtomAnnotation:
    id: int                        # fixed integer, not descriptive string
    deps: tuple[int, ...]          # tuple for frozen-safe hashability
    oracle: OracleType             # existing enum from models.py
    content: str
    synthetic: bool = False        # True for _preamble, _residual, monolithic
    start_offset: int = 0
    end_offset: int = 0
```

Synthetic atoms use reserved IDs: `0` for monolithic, `-1` for preamble, `-2` for
residual.

### 2.3 Parsing and Validation

`parse_atoms()` is the single entry point. It validates before returning:

1. Oracle values validated against `OracleType` enum — unknown → `LAYER3_LLM`
2. Atom count ≤ 12 — excess → fallback to monolithic with warning
3. No duplicate IDs — duplicate → fallback to monolithic
4. DAG validation on deps graph (Kahn's algorithm) — cycle → fallback to monolithic
5. Skip ATOM markers inside fenced code blocks (context-aware parsing)
6. ID values ≤ K declared in `K_ATOMS` — out-of-range → fallback
7. Any validation failure → log warning, return monolithic fallback

**Call-site restriction:** `parse_atoms()` is ONLY called on generator-produced
solution text. Never on verifier output, breaker output, or critique text.

### 2.4 Fallback Logic

When no atom annotations are found, fallback produces a single monolithic atom with
oracle level derived from existing sentinels using a **contiguity check** (not `max()`
on sparse keys):

```python
def parse_atoms(solution_text: str) -> list[AtomAnnotation]:
    atoms = _extract_atom_markers(solution_text)

    if not atoms:
        layer_results = parse_layer_results(solution_text)
        # Contiguity: longest run from L0
        depth = 0
        while depth in layer_results:
            depth += 1
        oracle = (ORACLE_BY_DEPTH[min(depth, 3)]
                  if depth > 0
                  else OracleType.LAYER3_LLM)
        return [AtomAnnotation(
            id=0, deps=(), oracle=oracle,
            content=solution_text, synthetic=True,
            end_offset=len(solution_text)
        )]

    # Orphan text before first atom → preamble (synthetic, id=-1)
    if atoms[0].start_offset > 0:
        preamble_text = solution_text[:atoms[0].start_offset]
        preamble_layers = parse_layer_results(preamble_text)
        preamble_depth = 0
        while preamble_depth in preamble_layers:
            preamble_depth += 1
        preamble_oracle = (ORACLE_BY_DEPTH[min(preamble_depth, 3)]
                           if preamble_depth > 0
                           else OracleType.LAYER3_LLM)
        atoms.insert(0, AtomAnnotation(
            id=-1, deps=(), oracle=preamble_oracle,
            content=preamble_text, synthetic=True,
            end_offset=atoms[0].start_offset
        ))

    # Orphan text after last atom → residual (synthetic, id=-2)
    if atoms[-1].end_offset < len(solution_text):
        residual_text = solution_text[atoms[-1].end_offset:]
        last_real = [a for a in atoms if not a.synthetic][-1]
        max_oracle = max(
            (a.oracle for a in atoms if not a.synthetic),
            key=lambda o: list(OracleType).index(o)
        )
        atoms.append(AtomAnnotation(
            id=-2, deps=(last_real.id,), oracle=max_oracle,
            content=residual_text, synthetic=True,
            start_offset=atoms[-1].end_offset,
            end_offset=len(solution_text)
        ))

    return atoms
```

**Key design decisions in fallback:**
- Contiguity check prevents gap-skipping exploit (L0+L2 present but L1 missing →
  effective depth is 0, not 2)
- Preamble oracle derived from sentinels in preamble text (not hardcoded L3)
- Residual oracle = max of all real atom oracles (not hardcoded L3) — prevents hiding
  the core claim in an under-verified synthetic atom
- `synthetic=True` on all fallback atoms — downstream code can filter

### 2.5 Sentinel Trust Model

Sentinels **reduce but don't eliminate** LLM scrutiny. The verifier is instructed:
"if L0-L2 checks pass, focus your effort on logic, citations, and the final result" —
not "skip verified atoms entirely." This prevents no-op verify functions from bypassing
LLM verification.

All `ALETHIC_L{N}_CHECK:` lines are **stripped** from CORRECTED SOLUTION blocks before
acceptance. Sentinels must only be trusted when extracted from the generator's
tool-execution output, not from LLM-written prose.

## 3. Section 2: Adversarial Breaker

### 3.1 Trigger Conditions

The breaker fires ONLY when:
- `Verdict.CORRECT` (not `MINOR_ISSUES` — let revision handle those)
- `confidence >= confidence_threshold`
- `adversarial_breaker` is True (enabled in `thorough`/`extreme` presets)
- Solution has real atom annotations (not monolithic fallback — no precision gain)

Safety guards:
- Wrapped in `try/except ContextExhaustedError` → treat as `NO_FLAW_FOUND`
- ContextExhaustedError must never discard a verified-CORRECT solution

### 3.2 Three-Tier Output

```
BREAKER_VERDICT: FLAW_FOUND | SUSPECTED_FLAW | NO_FLAW_FOUND
TARGET_ATOM: <atom integer, or 0 if whole-solution>
FLAW_TYPE: counterexample | logical_gap | missing_case | domain_violation
EVIDENCE: <specific counterexample, logical gap, or regime failure>
REASONING: <why this invalidates the claim>
```

- **FLAW_FOUND** — Python-confirmed counterexample OR explicit logical gap with formal
  statement. Demotes to `MAJOR_FLAW`, injects evidence + reasoning into revision
  critique. Confidence capped at 0.3.
- **SUSPECTED_FLAW** — possible issue without confirmed artifact. Appended to critique
  as advisory (`[BREAKER ADVISORY]`), does NOT demote confidence. Reviser sees it but
  isn't forced to act on it.
- **NO_FLAW_FOUND** — no effect on anything. One-directional filter: the breaker can
  only decrease confidence or do nothing. Sonnet's inability to find a flaw in an
  Opus-generated proof is weak evidence of correctness — NO confidence boost.

### 3.3 Expanded Mandate

The breaker is NOT limited to numerical counterexamples. It can find:

- (a) A concrete numerical counterexample to a universal claim
- (b) A logical step that does not follow from its premises
- (c) A theorem misapplied outside its domain of validity
- (d) A case not handled in a case analysis

This addresses the fundamental problem that proofs (e.g., "sqrt(2) is irrational")
have no counterexample — the breaker must also detect logical flaws. The terminology
uses `FLAW_FOUND` / `NO_FLAW_FOUND` (not `FALSIFIED` / `SURVIVED`) to reflect this
broader mandate.

### 3.4 Domain-Specific Breaker Prompts

Two system prompts, not one:

**Math breaker** focuses on:
- Universal claim falsification via small/boundary cases
- Structural inconsistency (degree mismatch, type errors)
- Dual representation disagreement (closed-form vs. direct computation)
- Logical gaps in proof steps

**Physics breaker** focuses on:
- Dimensional inconsistency (units mismatch)
- Known limit violations (c→∞, ℏ→0, T→0)
- Wrong sign of physical quantities (negative kinetic energy)
- Regime breakdown (formula invalid outside assumed domain)

Both prompts instruct the model to emit `ALETHIC_L{N}_CHECK:` format for programmatic
checks, maintaining compatibility with `parse_layer_results()`.

### 3.5 Attack Strategy: Roots First

```
Priority targeting (dependency order, roots first):
1. Atoms with deps=[] — axioms and base claims (no support → highest leverage)
2. Atoms with oracle=L3/L4 — least programmatically verified
3. Atoms whose oracle checks passed but downstream atoms failed
```

Attacking roots (atoms with no dependencies) is highest-leverage: falsifying a
widely-used base claim breaks the most downstream inferences. Attacking leaves
(conclusions) is lowest-leverage — it only tells you the answer is wrong, not why.

### 3.6 Output Parsing

The breaker has Python sandbox access (same as generator/verifier). The breaker prompt
includes an explicit instruction: "Produce your structured output (BREAKER_VERDICT,
TARGET_ATOM, etc.) in your FINAL message, AFTER all code execution." This ensures
`_extract_text()` captures the verdict from the last response content block,
matching the existing multi-round tool-use pattern in `_call_model()`.

Parsed by `_parse_breaker()` — same regex-per-field pattern as `_parse_verification()`.

### 3.7 Integration with Orchestrator

Two insertion points — one for the primary acceptance path, one for the FIXABLE-accepted
path:

```python
# Primary acceptance path (after is_acceptable)
if verification.is_acceptable(self.config.confidence_threshold):
    if self.config.adversarial_breaker and not is_monolithic_fallback(atoms):
        try:
            breaker_result = self._run_breaker(problem, solution, atoms)
        except ContextExhaustedError:
            breaker_result = BreakerResult(verdict=BreakerVerdict.NO_FLAW_FOUND)

        if breaker_result.verdict == BreakerVerdict.FLAW_FOUND:
            verification = VerificationResult(
                verdict=Verdict.MAJOR_FLAW,
                confidence=min(verification.confidence, 0.3),
                critique=(verification.critique + "\n\n"
                          + breaker_result.critique_addendum),
                issues=[...breaker_result.issues],
            )
            state.breaker_falsified = True
            state.record_event(EventType.BREAKER_FLAW_FOUND, ...)
            # Falls through to revision naturally

        elif breaker_result.verdict == BreakerVerdict.SUSPECTED_FLAW:
            verification = VerificationResult(
                verdict=verification.verdict,
                confidence=verification.confidence,  # unchanged
                critique=(verification.critique + "\n\n[BREAKER ADVISORY]\n"
                          + breaker_result.reasoning),
                issues=verification.issues,
            )
            state.record_event(EventType.BREAKER_SUSPECTED, ...)
            # Falls through to acceptance (confidence unchanged)

        else:
            state.record_event(EventType.BREAKER_SURVIVED, ...)

# Same pattern at FIXABLE-accepted path
```

### 3.8 Stall Detection Interaction

- `breaker_falsified` flag on per-iteration state
- Iterations where `breaker_falsified=True` are **excluded** from both stall detectors:
  - Detector 1: confidence plateau (`iterations_since_meaningful_improvement`)
  - Detector 2: consecutive `MAJOR_FLAW` verdicts
- Rationale: breaker falsifications indicate the breaker is working, not that the
  generator is stuck. False stall signals would waste compute on strategy resets.
- Atoms from breaker-falsified iterations are excluded from `atom_history`

### 3.9 Error Taxonomy Integration

New `"counterexample"` category added to `_TAXONOMY_KEYWORDS`:
```python
"counterexample": ["counterexample", "flaw found", "falsif", "regime failure"],
```

Targeted revision addendum:
```
A specific counterexample or logical flaw was found by the adversarial breaker.
Re-examine the targeted claim at the identified input or logical step. Either
refute the flaw (show why it does not actually violate your claim) or repair the
proof step that fails.
```

Breaker critique is appended to verifier critique BEFORE `classify_errors_routed()`
runs — reuses existing taxonomy routing machinery.

### 3.10 Autopsy Integration

New failure pattern: `"breaker_blocked"` — when CORRECT solutions are repeatedly
falsified by the breaker across multiple iterations. Detected by counting
`BREAKER_FLAW_FOUND` events in the event log.

## 4. Section 3: Atom-Aware Stall Recovery

### 4.1 Design Constraints

- No new API calls — prompt-only enhancement
- No partial regeneration — generator produces full solution
- No per-atom confidence — single verifier confidence score
- Falls back to v3.4 behavior when no atom annotations present
- **Disabled when variant-B is active** (incompatible atom schemas across models)

### 4.2 Atom ID Stability

Fixed integer IDs (1 through K) ensure cross-iteration comparability. Descriptive
names would drift across iterations (especially after stall resets that force
"categorically different approach"), making stability tracking inert.

### 4.3 Content Hashing

Hash only mathematical claim text, **stripping verification function bodies**:

```python
_VERIFY_FUNC_RE = re.compile(
    r'\n\s*```python\s*\ndef verify_.*?```', re.DOTALL
)

def content_hash(atom: AtomAnnotation) -> str:
    """Hash mathematical content only, stripping verify functions."""
    cleaned = _VERIFY_FUNC_RE.sub('', atom.content)
    cleaned = ' '.join(cleaned.split())  # normalize whitespace
    return hashlib.sha256(cleaned.encode()).hexdigest()[:16]
```

Without this, different test values in `verify_atom_N()` functions (chosen
stochastically at temperature=1.0) would cause hash changes on every iteration,
making every atom appear FAILING regardless of mathematical stability.

### 4.4 Stability Classification

```python
class AtomStability(enum.Enum):
    STABLE = "stable"
    OSCILLATING = "oscillating"
    FAILING = "failing"

def classify_atom_stability(
    atom_history: list[list[AtomAnnotation]],
    confidence_history: list[float],
    confidence_floor: float = 0.70,
) -> dict[int, AtomStability]:
    stability: dict[int, AtomStability] = {}

    for atom_id in all_atom_ids(atom_history):
        entries = [
            (content_hash(find_atom(iteration, atom_id)), conf)
            for iteration, conf in zip(atom_history, confidence_history)
            if find_atom(iteration, atom_id) is not None
        ]

        if not entries:
            continue

        hashes = [h for h, _ in entries]
        confs = [c for _, c in entries]

        if len(set(hashes)) == 1 and all(c >= confidence_floor for c in confs):
            # Consistent content AND appeared in high-confidence iterations
            stability[atom_id] = AtomStability.STABLE
        elif len(hashes) >= 2 and hashes[-1] in hashes[:-1]:
            # Current hash appeared before — cycling (any period)
            stability[atom_id] = AtomStability.OSCILLATING
        else:
            stability[atom_id] = AtomStability.FAILING

    return stability
```

**Key design decisions:**
- **Confidence-gated STABLE**: atom must appear in iterations with confidence ≥ 0.70
  to qualify. Prevents stable-atom-poisoning (consistently wrong atom protected from
  change).
- **Any-cycle oscillation detection**: `hashes[-1] in hashes[:-1]` catches period-2,
  period-3, and higher oscillations. Not just the simple `[-1] == [-3]` check.
- **Confidence history as parameter**: uses the existing per-iteration best confidence
  from `state.best_confidence`, no new tracking needed.

### 4.5 Generator Prompt on Stall Reset

```
STALL RECOVERY CONTEXT:

STABLE ATOMS (preserve verbatim — override ONLY if you believe this atom
is the root cause of downstream failures, and document why):
- atom_2: [L0 verified, stable across 3 iterations at confidence >= 0.82]

FAILING ATOMS (replace with fundamentally different approach):
- atom_4: previously failed approaches:
    1. Residue theorem with branch cut along negative real axis -> sign error
    2. Keyhole contour with epsilon-regularization -> divergent integral
  Do NOT retry these.

OSCILLATING ATOMS (cycling between forms — neither is correct):
- atom_3: cycling detected (period 2)
```

**Escape valve:** STABLE atoms carry an explicit override instruction to prevent the
stable-atom-poisoning lock-in. The generator can override a STABLE classification if
it believes the atom is the root cause — but must document why.

### 4.6 History Management

- `atom_history` capped at last `stall_window + 1` iterations (typically 4-5 entries)
- Store only content hashes in history, not full text strings
- Full content strings loaded from worklog files at prompt-injection time for
  FAILING/OSCILLATING descriptions only
- **Clear history on stall reset** — new "generation epoch" starts clean (avoids
  cross-approach contamination)
- Atoms from breaker-falsified iterations excluded

### 4.7 Variant-B Interaction

Atom stability tracking is **disabled** when `variant_b` is active. Rationale:
different models produce incomparable atom decompositions. Stability tracking across
Opus/Sonnet alternation is noise — every atom appears FAILING because the schemas
are incompatible.

When variant-B is disabled (via `--no-variant-b`), atom stability tracking activates
fully. This means variant-B diversity and atom stability are **alternative strategies**
for the same goal (avoiding convergence to a local minimum). Users choose one.

### 4.8 Checkpoint-Resume

Serialize `atom_history` to checkpoint as compact JSON:
```json
[{"id": 1, "content_hash": "a3f2...", "iteration": 3, "confidence": 0.85}]
```

Restore on resume; rebuild stability classifications from stored hashes.

### 4.9 Skill Parity

- Add `{atom_stability_context}` placeholder to skill orchestrator Step 2-pre
- Write `atom_history` to `session.json` under `"atom_history"` key
- Inject stability context during generator prompt construction in Step 2a when stall
  reset is active

## 5. Cross-Section Integration

### 5.1 Orchestrator Flow

```
+-----------------------------------------------------------------+
|                    Orchestrator Iteration                         |
|                                                                   |
|  +- Step 0: Stall Check ------------------------------------+    |
|  | _check_stall() — excludes breaker_falsified iterations    |    |
|  | If stall AND variant_b is None:                           |    |
|  |   classify_atom_stability(atom_history, conf_hist)        |    |
|  |   clear atom_history (new epoch)                          |    |
|  |   inject stability context into generator prompt          |    |
|  +-----------------------------------------------------------+    |
|                          |                                        |
|  +- Step 1: Generate N --+------+                                |
|  | Generator embeds ATOM[1..K] with deps, oracle, verify_*()  |  |
|  +------------------------------------------------------------+  |
|                          |                                        |
|  +- Step 2: Verify All N +------+                                |
|  | parse_atoms() on each candidate (validation + fallback)     |  |
|  | Verifier consumes sentinel results, focuses on L3+ atoms    |  |
|  | Select best candidate by confidence                         |  |
|  +------------------------------------------------------------+  |
|                          |                                        |
|  +- Step 3: Accept Gate -+------+                                |
|  | if is_acceptable(threshold):                                |  |
|  |   if adversarial_breaker AND not monolithic:                |  |
|  |     run breaker (Sonnet, domain-specific prompt)            |  |
|  |     FLAW_FOUND -> demote, set breaker_falsified=True        |  |
|  |     SUSPECTED_FLAW -> advisory only, no demotion            |  |
|  |     NO_FLAW_FOUND -> accept                                 |  |
|  |     ContextExhaustedError -> treat as NO_FLAW_FOUND         |  |
|  +------------------------------------------------------------+  |
|                          |                                        |
|  +- Step 4: Post-Iteration +----+                                |
|  | if not breaker_falsified:                                   |  |
|  |   append winner's atoms to atom_history                     |  |
|  |   (capped at stall_window + 1, content hashes only)         |  |
|  | Record events (BREAKER_FLAW_FOUND/SUSPECTED/SURVIVED)       |  |
|  | Update stall tracker (excluding breaker-falsified iters)    |  |
|  +------------------------------------------------------------+  |
+-----------------------------------------------------------------+
```

### 5.2 Minimum Viable Rollout

If shipping incrementally within v3.5:

1. **Section 1 alone** (atom annotations + parsing) — useful immediately as metadata
   for verifier attention-routing, foundation for everything else.
2. **Section 2 alone** (breaker without atoms) — degrades to whole-solution attack.
   Useful but less precise.
3. **Section 3 requires Section 1** — without atom annotations, stall recovery is
   always in v3.4 fallback mode.

Recommended order: **Section 1 → Section 2 → Section 3**.

## 7. Cost Analysis

### 7.1 Per-Preset Estimates

| Preset | Atom overhead | Breaker overhead | Stall recovery | Total |
|--------|--------------|------------------|----------------|-------|
| quick | +1-2% tokens | 0 (disabled) | 0 (disabled) | **1.02x** |
| default | +5-8% tokens | 0 (disabled) | 0 | **1.06-1.09x** |
| thorough | +12-18% tokens | +2-4% (Sonnet) | 0 (variant-B active) | **1.15-1.22x** |
| extreme | +10-15% tokens | +1-2% (Sonnet) | 0 (variant-B active) | **1.12-1.18x** |

Atom stability tracking adds zero API calls when active (prompt-only enhancement,
+200-500 generator prompt tokens for stability context). It activates only with
`--no-variant-b`.

### 7.2 v3.6 Cost Guardrail

Per-atom verification in v3.6 MUST NOT introduce independent API calls per atom.
An 8-atom solution with N=3 candidates would produce 24 verifier calls per iteration
instead of 3 — an 8x cost explosion. The established pattern (embed atom outputs in
solution text, consume all outputs in a single LLM verifier pass) must be preserved.

### 7.3 Benchmark Gating for v4.0

Gate formula: `(delta_solve_rate / baseline_solve_rate) > (delta_cost / baseline_cost)`

The proportional quality improvement must exceed the proportional cost increase. If
atom annotations show ≥10% solve-rate improvement on the eval harness, proceed to
Option E full rewrite (v4.0). If marginal, stay with Option F extended (atom-annotated
solutions with PUCT tree search overlay).
