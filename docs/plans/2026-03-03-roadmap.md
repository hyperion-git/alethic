## Tier 1: Near-term (v3.2 — target: weeks)

### 1.1 Web search integration for CLI [M]

**Status:** Pending idea since v3.0.5. Already noted as highest-priority future work.

**Motivation:** The Aletheia paper (arXiv:2602.10177) found web search was their most
valuable tool — more impactful than Python execution — for reducing citation
hallucinations. Skills already have WebSearch via Claude Code; the Python library/CLI
has no search capability.

**Approach:**
- Query planner: decompose problem into search queries (theorem names, identities, constants)
- Source ranking: prefer arXiv, Wikipedia, MathWorld, DLMF, NIST
- Quote extraction: pull exact statements with source attribution
- **Literature injection**: retrieved theorems and proofs must be injected directly into the
  generator's system prompt context — not just used for post-hoc citation checking. Woodruff
  et al. (arXiv:2602.03837) found this was the mechanism that actually improved proof quality.
- Citation spans: verifier can cross-reference claims against retrieved sources
- Freshness checks: flag if a cited result has known errata

**API options:** Brave Search API (free tier, simplest), or Tavily (better for research).

**Impact:** Major reduction in citation hallucinations and "it is well known" vagueness.

### 1.2 Error taxonomy-driven revision policies [S-M]

**Motivation:** Currently the Reviser gets a single undifferentiated prompt regardless of
error type. Algebraic slips, logical gaps, citation issues, and interpretation errors need
fundamentally different repair strategies.

**Approach:**
- Classify verifier issues into categories: algebra, logic, citation, interpretation, units, missing-case
- Map each category to a specialized revision prompt (e.g., "re-derive this step from scratch" vs "find and cite the source")
- The orchestrator selects the revision prompt based on the dominant error category

**Impact:** Higher revise-loop efficiency — fewer wasted revision cycles on mismatched repair strategies.

### 1.3 Backward verification [S-M]

**Motivation:** Current verification is forward-only (check premises → conclusion). Backward
verification asks: "can this answer imply the given constraints?" — catching non sequiturs
where the conclusion is valid but disconnected from the premises.

**Approach:**
- Add a backward-check pass to the verifier: given the final answer, attempt to reconstruct the problem constraints
- Flag if the answer satisfies a weaker or different problem than stated
- Complements existing problem-interpretation checking (anti-specification-gaming)

**Impact:** Catches a class of errors that forward verification misses entirely.

### 1.5 Negative prompting for failed-method exclusion [S]

**Motivation:** Alethic's stall reset already tracks `failed_approaches` and injects a
`STRATEGY_RESET_ADDENDUM` encouraging different strategies. However, the language is soft.
Brenner et al. (arXiv:2603.04735) demonstrate that *explicit prohibition language* is more
effective: "Do NOT use [method X]. Reflect on your plan and if your plan uses this method
try a different plan."

**Approach:**
- Reformat the `failed_approaches` list in the stall reset prompt from advisory ("approaches
  that haven't worked") to explicit prohibition ("DO NOT use these methods")
- Use the paper's exact prohibition template as the model
- Apply to both the Python library (`_build_reset_context()`) and the skill orchestrator's
  stall reset branch
- No new infrastructure required — this is a prompt engineering change to existing stall logic

**Impact:** Stronger strategy diversification during stall recovery, directly motivated by a
working physics discovery system. Low risk, high leverage.

**Reference:** Brenner, Cohen-Addad, Woodruff (arXiv:2603.04735) §3, Appendix A.3

### 1.4 Autopsy mode for failed loops [S-M]

**Motivation:** When a solve/derive loop exhausts iterations and returns UNSOLVED, there's
no structured analysis of *why* it failed. Users get the best attempt but no diagnostic.

**Approach:**
- Post-loop analysis: classify failure pattern (oscillation, stall, regression, persistent flaw)
- Generate a structured "autopsy report" with: failure category, confidence trajectory, dominant error types, strategy reset history
- Suggest concrete next steps (reformulate problem, increase N, try different preset, provide hints)
- Write to session directory as `worklog/autopsy.md`

**Impact:** Transforms opaque failures into actionable feedback.

### 1.7 Generator prompt hardening [S]

**Motivation:** Two behavioral patterns identified by Woodruff et al. (arXiv:2602.03837)
that Alethic's generator prompts should address:

1. **Context de-identification**: Models presented with a problem framed as "open" or
   "unsolved" often refuse to engage, treating it as beyond their capability. When the same
   problem is presented as a neutral imperative ("prove that…", "derive…"), models engage
   and often succeed. Alethic's generator prompts should strip or avoid language that
   signals difficulty ("this is an open problem", "researchers have struggled with…").

2. **Minimal dimension first for counterexample search**: The balanced prompting addendum
   already asks generators to check whether a claim might be false. Woodruff et al. show the
   most effective strategy is to search for counterexamples at the smallest possible
   dimension first (e.g., n=2, n=3) and verify exhaustively across all cases before scaling.
   This heuristic should be added explicitly to the balanced addendum.

**Approach:**
- Audit generator system prompt for any language implying difficulty or open status; replace
  with neutral imperative framing
- Add "start counterexample search at minimal dimension and verify exhaustively" to the
  balanced prompting addendum in `prompts.py`, `physics_prompts.py`, and skill reference files

**Impact:** Reduces refusal/under-confidence patterns in the generator; improves
counterexample detection rate on conjecture-type problems.

**Reference:** Woodruff et al. (arXiv:2602.03837) §2.7 (context de-identification), Case Study 1

### 1.6 Executable intermediate steps [M]

**Motivation:** Alethic currently verifies complete solutions. Brenner et al. (arXiv:2603.04735)
show that requiring each reasoning step to emit a testable Python function (alongside LaTeX)
enables automated step-level numerical verification — their system auto-pruned 80% of
erroneous branches before they could propagate, dramatically improving search efficiency.

**Approach:**
- Prompt the generator to produce a `verify_step_N(params)` Python function for each major
  intermediate result (e.g., after each key integral, identity substitution, or limit)
- The sandbox evaluates each step function immediately against numerical ground truth
- Steps that fail numerical checks are flagged in the verifier critique with the exact error
- For physics: test dimensional consistency and limiting cases at each step
- This is a prerequisite for 3.1 (tree search) and 3.3 (process supervision)

**Impact:** Catches algebraic errors early (before they propagate), reduces wasted revision
cycles, and creates the infrastructure needed for future step-level tree search.

**Reference:** Brenner, Cohen-Addad, Woodruff (arXiv:2603.04735) §2–3

## Tier 2: Medium-term (v3.3–v3.4 — target: months)

### 2.1 Programmatic physics verifier stack [M]

**Motivation:** Physics derivations have verifiable structural properties that LLM-only
verification misses: dimensional consistency, correct limiting cases, symbolic-numeric
agreement.

**Approach:**
- Dimensional analysis checker: parse equations, verify units balance (via sympy.physics.units)
- Limiting case validator: automatically test known limits (e.g., c→∞, ℏ→0, T→0)
- Symbolic-numeric cross-check: evaluate key expressions both symbolically and numerically, flag disagreements
- Integrate as additional verification pass (runs in sandbox alongside LLM verifier)

**Impact:** Catches "looks right to an LLM" physics errors that are mechanically detectable.

### 2.2 Metamorphic verification [M]

**Motivation:** A correct solution should be invariant under re-parameterization, coordinate
transforms, and equivalent formulations. Testing this invariance catches hidden errors.

**Approach:**
- Generate metamorphic variants of the problem (e.g., rename variables, switch coordinate systems, use equivalent definitions)
- Verify the solution under each variant
- Flag inconsistencies between variants

**Impact:** Strong hidden-error detection that's orthogonal to standard verification.

### 2.3 Evaluation harness with benchmark gating [M]

**Motivation:** No automated way to detect regressions or measure improvement. Changes to
prompts, presets, or logic could silently degrade quality.

**Approach:**
- Curated benchmark suite: MATH subset, GSM8K-hard, physics derivation set, citation accuracy cases
- Automated scoring pipeline: run benchmarks, compare verdicts/confidence against ground truth
- CI integration: gate releases on benchmark scores (no regression allowed)
- Track metrics over time: solve rate, iteration count, stall frequency, cost per problem

**Impact:** Prevents regressions, enables data-driven prompt/architecture decisions.

### 2.4 Adaptive compute allocation [M]

**Motivation:** Currently N (best-of-N) and K (verifiers) are fixed per preset. Easy problems
waste compute; hard problems are under-resourced.

**Approach:**
- Difficulty estimator: use first-iteration confidence + error taxonomy to classify difficulty
- Dynamic N: start with N=1, escalate to N=3+ if first candidates fail
- Dynamic K: use K=2 for high-confidence results, K=5+ for borderline cases
- Budget cap: total cost ceiling per problem, with graceful degradation

**Impact:** Better quality-cost frontier — spend compute where it matters.

### 2.5 Adversarial breaker model [M]

**Motivation:** Current verification asks "is this solution correct?" A complementary approach
asks "how can I break this solution?" — actively searching for counterexamples and edge cases.

**Approach:**
- After verification passes, run a "breaker" agent that tries to find counterexamples, boundary failures, or specification-gaming interpretations
- If the breaker succeeds, feed the counterexample back to the revision loop
- Use a different model (e.g., Sonnet) for diversity, similar to variant-B

**Impact:** Stronger robustness, especially against subtle errors that pass standard verification.

### 2.7 Multi-round adversarial verifier self-correction [M]

**Motivation:** Alethic's K parallel verifiers each evaluate once and independently.
Woodruff et al. (arXiv:2602.03837, Case Study 2) demonstrate a complementary technique:
a *single verifier* that iterates internally, critiquing its own initial assessment for
hallucinations before committing to a verdict. This catches errors in the verification
itself — the verifier hallucinating a valid proof step where none exists. Applied to a
cryptography paper, this protocol identified a fatal gap that peer review had missed.

**Approach:**
The verifier prompt is restructured into a multi-round internal dialogue:
1. Generate initial assessment (current behavior)
2. Self-critique: "Review your assessment — did you hallucinate any proof steps? Did you
   accept vague claims without checking them?"
3. Revise the assessment based on self-critique
4. Second-round refinement: "Are there any remaining unverified steps?"
5. Final output using explicit completeness tags: distinguish **COMPLETE PROOF** (every
   step verified) from **STRUCTURED PARTIAL PROGRESS** (valid skeleton, gaps remaining)

This is orthogonal to K parallel verifiers — the two compose: K verifiers each running
the adversarial self-correction protocol gives both breadth (diversity) and depth (rigor).

**Implementation:**
- Add a `adversarial_self_correction: bool` field to `VerifierConfig` (default off, enabled
  in `thorough` and `extreme` presets)
- Restructure the verifier prompt to include the 5-step internal protocol
- Update `COMPLETE PROOF` / `STRUCTURED PARTIAL PROGRESS` tags in verdict parsing
- Apply to both `subagents.py` verifier and the skill verifier reference prompt

**Impact:** Catches verifier hallucinations — a category of error that K-diversity alone
cannot address, since multiple verifiers can share the same blind spot.

**Reference:** Woodruff et al. (arXiv:2602.03837) §2, Case Study 2 (SNARG bug detection)

### 2.6 Confidence calibration layer [M]

**Motivation:** Verifier confidence scores are uncalibrated — 0.9 from one run may not mean
the same as 0.9 from another. Threshold tuning is currently manual.

**Approach:**
- Collect (confidence, actual_correctness) pairs from benchmark runs
- Fit a calibration curve (Platt scaling or isotonic regression)
- Apply calibration to raw verifier scores before threshold comparison
- Per-domain, per-difficulty calibration curves

**Impact:** Fewer false accepts/rejects, more meaningful confidence thresholds.

## Tier 3: Long-term (v4.0+ — target: quarters)

### 3.1 Verifier-guided tree search [L]

**Motivation:** Current best-of-N generates N complete solutions, then picks the best.
Tree search would expand partial solutions, pruning unpromising branches early.

**Approach:**
- Each tree node = a proposed intermediate expression (LaTeX) + an executable Python function
  (`verify_step_N(params)`) that evaluates it numerically — the exact architecture used by
  Brenner et al. (arXiv:2603.04735), who explored ~600 nodes and pruned 80% automatically
- Use PUCT scoring (predictor + upper confidence bound) to balance exploitation and
  exploration across candidate expansion paths
- After each node, run the sandbox verifier: if numerical agreement fails, inject traceback
  and absolute error back into LLM context and prune the branch
- Negative prompting to force exploration of distinct solution families (see 1.5)
- Combine with best-of-N at each branch point

**Impact:** Much better performance on long, multi-step proofs/derivations. Fundamental
architecture shift from whole-solution to incremental verification. Brenner et al. show
this working in practice for an open physics problem.

**Prerequisites:** Executable intermediate steps (1.6), structured solution format.

**Reference:** Brenner, Cohen-Addad, Woodruff (arXiv:2603.04735) §2–3

### 3.2 Formal proof obligation checker [XL]

**Motivation:** Bridge between LLM-generated proofs and formal verification systems.
For claims that can be expressed in Lean or Isabelle, verify them mechanically.

**Approach:**
- Identify formalizable claims in solutions (existential/universal statements, inequalities, identities)
- Auto-translate to Lean 4 proof obligations
- Run Lean type-checker on obligations
- Feed failures back as high-confidence verifier issues

**Impact:** Massive correctness gains on theorem-style tasks. But very high complexity.

### 3.3 Process-supervised scoring [L]

**Motivation:** Current verification scores final answers only. Process supervision rewards
intermediate reasoning states, catching errors earlier and guiding revision more precisely.

**Approach:**
- Train/few-shot a step-level scorer on intermediate reasoning
- Integrate step scores into candidate ranking (not just final verdict)
- Use step scores to guide revision (target specific weak steps)

**Impact:** Better long-horizon reasoning, more efficient revision.

### 3.4 New domains [M-L each]

Potential domain expansions, each requiring domain-specific prompt templates and verifiers:

- **Competitive programming**: correctness + complexity verifier pair (run test cases + verify time/space claims)
- **Engineering analysis**: control, circuits, statics, fluids (domain verifiers with dimensional/numerical checks)
- **Quantitative finance**: stochastic calculus sanity + Monte Carlo simulation checks
- **"Reproduce this paper" mode**: derive + verify + source-trace against original paper

## Tier 4: Infrastructure & Developer Experience

### 4.1 Caching and artifact reuse [S-M]

- Verifier result cache (same solution text → same verification, skip re-run)
- Retrieval cache for web search results
- Checkpoint dedup across sessions

### 4.2 Observability stack [M]

- Per-stage latency tracking
- Verifier disagreement rates
- Stall pattern analysis
- Failure taxonomy dashboard
- Cost breakdown per problem

### 4.3 CI integration [S-M]

- `alethic verify --diff` for math-heavy docs/code comments/specs
- GitHub Action for automated verification on PR

### 4.4 Plugin API for custom verifiers [M]

- Public interface for registering custom verifier/generator/aggregator functions
- Enable community-contributed domain-specific verifiers
- Plugin discovery and composition

### 4.5 Structured output contracts [S]

- JSON schema for all outputs (solutions, verifications, consensus results)
- Provenance graph (which generator, verifier, revision produced each part)
- Machine-to-machine integration support
