## Decision 1 (D4): Which `verify()` call sites receive the atom focus directive?

### Context

In v3.5, all three `verify()` call sites pass `extra_system=self._adversarial_addendum()`.

In v3.6, `_build_atom_focus_directive(state.atom_history[-1])` should be combined with the adversarial addendum as `extra_system = _combine(adversarial_addendum, directive)`.

The three call sites are:

**Call site A** (`_verify_candidates()`, line ~521):
The main per-candidate verification. Called once per candidate per iteration. `atom_history` at this point contains atoms from ALL prior iterations (last entry = prior iteration's atoms). This is where the focus directive has the most value: directing the verifier's attention based on what was stable/failing in prior iterations.

**Call site B** (`_run_revision_loop()`, line ~607):
Re-verifies the revised solution after each revision. Called 0–N times per iteration (up to `max_revisions`). `atom_history` at this point STILL contains the prior iteration's atoms (current iteration's atoms have not been appended yet — appending happens at line 930, after `_verify_candidates` returns). The revised solution may have different atom structure than what was verified in call site A.

**Call site C** (FIXABLE shortcut, line ~1073):
Re-verifies the corrected solution from the verifier (when FIXABLE verdict was returned). Called at most once per candidate. The corrected solution was produced by the verifier itself — its atom structure may be unknown (the verifier does not annotate the corrected solution with ATOM markers).

### Options

**Option 1**: All three call sites receive the directive.
- Pros: Consistent; atom focus is always active wherever verification happens
- Cons: Call site B's directive is based on the PREVIOUS iteration's atoms, not the current revised solution's atoms. Call site C's directive may reference atoms that don't exist in the corrected solution.

**Option 2**: Call site A only.
- Pros: The directive is most meaningful for per-candidate main verification. Revision re-verify and FIXABLE re-verify are focused tasks (did the revision fix the identified issue?) and don't benefit from prior-iteration atom focus.
- Cons: Revision re-verify gets no atom context even when atom stability would be relevant.

**Option 3**: Call sites A and B (not C).
- Pros: Both primary verification types get context. FIXABLE re-verify is excluded because the corrected solution's atom structure is unknown.
- Cons: Call site B uses stale prior-iteration atoms for a revised solution.

## Decision 2 (D8): How should the atom-focus directive handle the monolithic fallback?

### Context

`parse_atoms()` in `atoms.py` always returns at least one atom. When the solution text has no `ATOM[N] deps=[...] oracle=LN` annotations, it falls back to returning `[AtomAnnotation(id=0, synthetic=True, oracle=LAYER3_LLM)]` (the monolithic atom representing "the solution as a whole, undecomposed").

The `_build_atom_focus_directive(atoms)` function filters `if not a.synthetic` — excluding all synthetic atoms. When all atoms are synthetic (the monolithic fallback), the function returns `None`. No directive is injected.

This means: **for solutions without explicit atom annotations, the atom-guided verification feature never engages**. Since the generator is not required to produce atom annotations, this could be the majority of solutions in practice.

### Options

**Option A**: Relax the synthetic filter — allow FAILING/OSCILLATING monolithic atoms to enter the HIGH tier.
- Implementation: `if a.oracle in HIGH_ORACLES or (a.stability != STABLE and a.id == 0):` (special-case monolithic)
- Pros: Feature engages even for unannotated solutions
- Cons: The monolithic atom has `oracle=LAYER3_LLM` (not a sentinel-based oracle). The directive would say "HIGH attention to atom 0" which gives the verifier no structural guidance — just "look hard at everything," which is already what the verifier does by default.

**Option B**: Inject a generic "full scrutiny" directive when confidence is declining and solution is monolithic.
- Implementation: if `_build_atom_focus_directive` would return `None` AND the winning candidate's confidence is below a threshold (e.g., < 0.80), inject a generic message: "No stable atom structure identified — apply full scrutiny to all steps."
- Pros: Feature provides signal even without annotations
- Cons: The generic message adds noise when the verifier already applies full scrutiny by default. The adversarial addendum already instructs multi-round self-critique.

**Option C**: Document explicitly that atom-guided verification is annotation-dependent. Strengthen the generator prompt to encourage (but not require) atom annotations.
- Implementation: Add to `GENERATOR_SYSTEM`: "For complex multi-step derivations, add `ATOM[N] deps=[...] oracle=LN` markers at each key claim. These enable targeted verification in subsequent iterations."
- Pros: Clean design boundary. Feature provides high-value directives when present, and gracefully degrades when absent.
- Cons: Generator annotation compliance is stochastic — depends on model following prompt instructions. The feature may still rarely engage for short/simple problems.

**Option D**: Treat the monolithic atom as ALWAYS needing full verification — add it to HIGH tier unconditionally when it's FAILING or OSCILLATING, regardless of synthetic flag.
- Implementation: `high_tier = [a for a in atoms if not a.synthetic and a.oracle in HIGH_ORACLES] + [a for a in atoms if a.synthetic and a.id == 0 and stability.get(0) in (FAILING, OSCILLATING)]`
- The directive for the monolithic atom would be: "ATOM[0]: full solution is oscillating/failing — full scrutiny required"
- Pros: Explicitly actionable. The verifier knows the whole solution is struggling, not just that verification should happen.
- Cons: This is essentially equivalent to "always full scrutiny when confidence is failing," which doesn't add information over the existing MAJOR_FLAW handling.
